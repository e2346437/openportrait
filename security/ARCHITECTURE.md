# Security architecture

What matters for security in OpenPortrait, as it exists in the code today (commit `1601f66`). Everything here was read from
the source or observed on a running sandbox; nothing is assumed. Changes that matter for security should update this file.

## Shape of the system

One container, one Node 22 process (Fastify), one SQLite database, plus two helpers started by the entrypoint.

```
                 internet                                         home / office network
                    │                                                      │
        Cloudflare edge (TLS, WAF)                                  browsers, cameras, AI apps
                    │ outbound tunnel                                      │
        ┌───────────▼──────────────────────────────────────────────────────▼───────────┐
        │ container                                                                    │
        │  tini (PID 1, root) → entrypoint.sh (root: chown /config /cache, set ids)    │
        │       └─ gosu → node main.js  (uid = PUID, no capabilities)                  │
        │                    ├─ HTTP  :8080  Fastify: staff API, client pages, /mcp,    │
        │                    │               /oauth, webhooks, static web app          │
        │                    ├─ SFTP  :2222  camera upload (ssh2), optional             │
        │                    ├─ FTP/FTPS :2121 + passive 30000-30009, optional          │
        │                    ├─ jobs (SQLite-backed), folder watcher, backups           │
        │                    └─ cloudflared (child process, token from settings/env)    │
        └──────────────┬──────────────┬──────────────┬──────────────┬──────────────────┘
                    /config        /galleries      /incoming       /cache
              SQLite, secret.key,   photo shoots   camera uploads   previews
              host key, backups     (read+write)   (write)          (disposable)
```

Languages and frameworks: TypeScript, Fastify 5, React/Vite (served as static files), Drizzle ORM on better-sqlite3-style
SQLite, `sharp` for images, `ssh2` and `ftp-srv` for camera upload, `@modelcontextprotocol/sdk` for MCP, `@node-rs/argon2`
for passwords, `nodemailer` for email. 209 HTTP routes are registered (167 staff, 13 public, 10 client-gallery, 6 OAuth, 3 MCP, 10 other such as health,
logo and media; static files are served separately). The route list is regenerated by the test harness on every run, so it can't drift.

## Trust boundaries

| # | Boundary | Who is on the far side | What crosses it | Enforced by |
|---|---|---|---|---|
| B1 | Internet or LAN → HTTP :8080 | Anyone | Requests | Per-route auth hooks; rate limits; Cloudflare in front when tunnelled |
| B2 | Staff session → staff API | The studio owner | Cookie `op_session` (HttpOnly, SameSite=Lax) | `onRequest` session lookup, `requireUser` / `requireOwner` |
| B3 | Client link → client gallery | Clients holding a private link | Slug in the URL, signed media URLs, optional password, `op_client` cookie | `load()` in `client-gallery.ts`, HMAC signatures |
| B4 | AI app → `/mcp` | An AI assistant acting for the owner | Bearer token (`opai_…`), OAuth 2.1 + PKCE | `authenticate()`, tool registry filtered by level and area, approval queue |
| B5 | Camera → SFTP/FTP | A camera with a per-camera login | Files, folder names | Per-camera login, path jail, no read/delete |
| B6 | Payment processor → webhook | PayPal | Signed events | Verification call to PayPal; app never trusts the body alone |
| B7 | App → outside | Cloudflare, SMTP server, Google, PayPal | Credentials, mail, calendar data | Secrets encrypted at rest; TLS to the far side |
| B8 | App process → host | The Docker host | Volumes, ports, capabilities | Container settings (see `DOCKER_HARDENING.md`) |
| B9 | Extension modules → app | Code the owner placed in `/config/extensions` | Full process privileges | Trust decision: same level as the container itself |
| B10 | Deployment ↔ deployment | Another customer's container, when one operator hosts several | Nothing should cross | Separate volumes, keys, networks (tested, `AUDIT_REPORT.md` section 6) |

The single most important property: **there is one role of consequence.** Setup creates one owner; no other user can be
created in this build. So "cross-account access" inside one deployment doesn't exist today; the equivalent risk is
cross-*deployment* access, which is tested separately. If multi-user is added, the authorization suite in
`apps/server/test/security/authz.test.ts` is the place to extend first.

## Authentication and sessions

- **Staff:** email + password. Argon2id (19 MiB, 2 passes). Login for an unknown email burns the same hashing time as a
  real one, and the response text is identical (tested, AUTHZ-5). Failed logins and successful ones go to `audit_log`.
- **Session:** 32 random bytes, stored only as a SHA-256 hash; 30-day fixed life; deleted on logout; all other sessions
  are deleted on password change. A new token is issued at every login (no fixation, AUTHZ-4). No idle timeout, no MFA.
- **Cookie flags:** `HttpOnly; SameSite=Lax`; `Secure` is set when the request arrived over HTTPS or carries Cloudflare's
  `cf-ray` header. Over plain HTTP on the LAN it is not set.
- **Setup:** `POST /api/studio/setup` is open until the first user exists. It is rate limited and transactional (two
  browsers can't both win) but it needs no proof of ownership (SEC-002).
- **Password recovery:** there is no web reset flow. The `openportrait` CLI inside the container resets a password, so
  recovery requires shell access to the container. That removes the reset-token attack class entirely.
- **Client galleries:** a private link (slug) is the credential. Optional per-gallery password (Argon2id), checked at a
  rate-limited endpoint, remembered in an HMAC-signed cookie that stops working when the password changes. Visitors
  identify with an email address that is **not verified** (SEC-012).
- **Camera logins:** per-camera username + 16-character generated password (Argon2id) or an SSH public key; six
  failures from one address in 10 minutes trigger a 15-minute block (in memory, reset on restart).

## Authorization model

- Everything under `/api/studio` goes through `requireUser`; owner-only settings use `requireOwner`. A test enumerates every
  registered route and asserts that an anonymous request gets 401 (AUTHZ-1: 162 protected staff routes at the time of writing).
- Object-level checks inside client pages are by gallery: favorites, downloads and photos are always looked up with the
  gallery id from the already-validated slug, so a photo id from another gallery returns 404.
- **MCP** reuses the same domain services as the staff API but is a separate door with its own rules: see `MCP_SECURITY.md`.

## Secrets and keys

| Secret | Where it lives | Protection |
|---|---|---|
| Instance key | `/config/secret.key` (0600), 32 random bytes | Plain file; encrypts the rest and derives HMAC subkeys |
| PayPal, Google, SMTP, tunnel token | SQLite `settings` | AES-256-GCM with the instance key |
| Passwords (staff, gallery, camera) | SQLite | Argon2id |
| Session tokens, AI tokens, OAuth codes, refresh tokens | SQLite | SHA-256 of the token only |
| SSH host key | `/config/sftp_host_ed25519_key` (0600) | Plain file |
| Signed media URLs, client cookies | Derived by HMAC-SHA256 from the instance key | Purpose-separated subkeys |

The key sits in the same folder as the database and its backups (SEC-015). Backing up `/config` as a unit therefore
backs up the key with the data it protects. The encryption is protection against someone who copies the database file
alone, not against someone who copies the folder.

## Data at rest

SQLite file in `/config` (WAL mode), a nightly online backup (14 kept) in `/config/backups`, photos on the share. Nothing
is encrypted at the volume level; that is the host's job. The audit log keeps staff and AI actions, including the
arguments of every AI tool call (useful, and also personal data: it is covered by the same backup).

## Background workers and integrations

- **Jobs** (SQLite-backed): thumbnails/previews (`sharp`), email sending, Google calendar sync, backups.
- **Folder watcher** (`chokidar`) over `/galleries`.
- **cloudflared**: spawned as a child process with the tunnel token; the only `child_process` use in the app.
- **Outbound requests:** PayPal API (fixed hosts), Google APIs, SMTP to a host the owner configures, and a self-check
  `fetch` of the owner's own public address (`/api/studio/internet/check`). Only the last two take an address from
  settings, and both are owner-only.
- **Extensions:** ES modules in `/config/extensions/*.mjs` are imported at start with full privileges. The loader logs a
  SHA-256 of each file. Anyone who can write to that folder can run code in the container, which is by design and equal
  to having shell access to it.

## Logging and monitoring

Fastify request logs (method, URL, status, timing; no headers or bodies), `audit_log` rows for sign-ins, settings changes,
AI calls, approvals and camera-server blocks, and a health endpoint (`/api/health`, which also returns a non-secret
instance id). There is no alerting; the owner reads Settings → Connect your AI → Activity and the container log.
